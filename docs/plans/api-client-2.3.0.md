# Bump donations-api-client to 2.3.0

## Context

The frontend pins `@jorgetroya80/donations-api-client@2.2.0`. The newest published version is
**2.3.0** (2026-10-23). The client's version always matches the API release tag.

What changed in `donations-api` between `v2.2.0` and `v2.3.0`:

| Commit    | Change                                                                                                                                  | Effect on the client                                                                                                                       |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `6c36fc9` | Java 25 upgrade (#56): toolchain, `Dockerfile`, CI                                                                                      | None. No controller, DTO or `packages/api-client/` file is touched.                                                                        |
| `e755579` | Clean-code pass (#55): filter-chain problem bodies go through a new `writeProblem()`; not-found lookups go through a new `getOrThrow()` | None on types. At runtime the 401 and the `PASSWORD_CHANGE_REQUIRED` 403 keep the same fields, and not-found `detail` texts are unchanged. |

The 2.2.0 plan flagged `e755579` as "check when 2.3.0 ships". It is checked here.

Evidence:

- `diff -ru` of the 2.2.0 and 2.3.0 `dist/` is **empty (0 lines)**. The generated contract is
  identical.
- `writeProblem()` sets `status`, `title`, `detail`, `instance`, extras (`code`) and then
  `requestId`, which are the same fields as the inline code it replaces. `SecurityIntegrationTest`
  now also asserts `status`, `title` and `instance` on the 403.
- `getOrThrow(id, label)` builds `"$label not found with id: $id"`, the same string as every
  `NotFoundException` it replaces (Donation, Donor, Expense, User).

Frontend code that depends on these runtime shapes, all unaffected:

- `src/lib/api.ts:33`: reads `body.code === 'PASSWORD_CHANGE_REQUIRED'`.
- `src/lib/api.ts:46` and `src/features/auth/login-page.tsx:43`: branch on HTTP 401.
- `src/lib/get-problem-message.ts`: reads `detail`, `title`, `status`, `requestId`.

**Outcome:** the frontend runs on client 2.3.0 with no code changes in `src/`.

## Decisions

- **No code changes.** The type diff is empty and the runtime error shapes the frontend reads
  are unchanged, so any edit in `src/` would be scope creep.
- **Commit type `fix(deps):`**, matching the 2.2.0 bump (#192), so release-please cuts a patch.

## Phases

### Phase 1: Bump (`fix(deps):`)

1. Done: on branch `chore/api-client-2.3.0`, `pnpm add -E @jorgetroya80/donations-api-client@2.3.0`.
2. Done: `diff -ru` against the 2.2.0 snapshot is empty.
3. Run `pnpm run check`, `pnpm run typecheck`, `pnpm run test` and `pnpm run build`.
4. Commit `fix(deps): bump donations-api-client to 2.3.0` together with this plan, then open a PR.

**Acceptance criteria:** `package.json` and `pnpm-lock.yaml` pin 2.3.0, all four checks pass,
and the PR CI is green.

### Checkpoint

- [ ] Optional smoke test against an API running 2.3.0 (local fullstack): log in, list donors,
      donations and expenses, open a non-existent donor id (expect the not-found message), and
      log in with a `must_change_password` user (expect the redirect to the password change).

## Risks

| Risk                                                            | Impact | Mitigation                                                                             |
