# Bump donations-api-client to 2.2.0

## Context

The frontend pins `@jorgetroya80/donations-api-client@2.0.0` (`package.json`, exact pin via
`.npmrc` `save-exact=true`). The newest published version is **2.2.0** (2026-09-21). The
client's version always matches the API release tag: `donations-api`'s `release.yml` runs
`pnpm version <tag>` and publishes `packages/api-client` on every release, and the 2.1.0 and
2.2.0 release runs both succeeded.

What changed in `donations-api` between `v2.0.0` and `v2.2.0`:

| Release | Change                                                                             | Effect on the client                                                                                                              |
| ------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 2.1.0   | Structured event logging (#48), new `RequestIdFilter`                              | None on types. At runtime every ProblemDetail (including the 401 from `SecurityConfig`) gains an extension property, `requestId`. |
| 2.2.0   | Kotlin 2.2.21 → 2.4.20 (#53), dropped `-Xannotation-default-target=param-property` | Probably none. 2.4 makes that annotation target the default, so validation annotations should land in the same place.             |

The compare diff touches no controller, DTO, `packages/api-client/` file or
`openapi-ts.config.ts`. The OpenAPI spec, and therefore the generated client, is **expected to be
identical**. This is a dependency bump that should need no code changes. The plan's job is to
prove that, not assume it.

Not in scope: `e755579 refactor: clean-code pass on services and problem responses (#55)` is on
the API's `main` but unreleased. It touches problem responses, so check it when 2.2.1 or 2.3.0
ships.

**Outcome:** the frontend runs on client 2.2.0, with evidence that the generated types did not
change, plus an optional follow-up that surfaces `requestId` to users.

## Decisions

- **Bump straight to 2.2.0**, skipping 2.1.0. Neither release changes the contract, so an
  intermediate step proves nothing.
- **Use a type diff as the gate, not only typecheck.** `tsc` passing proves the code still
  compiles. It does not catch a field becoming optional that the UI treats as always present
  when the types were already loose. Diffing `dist/*.d.ts` catches every contract change.
- **Commit type `fix(deps):`**, matching recent dependency bumps (#187, #189), so
  release-please cuts a patch.
- **Keep `requestId` UX in a separate PR (Phase 2).** It is a feature, it needs product input
  (whether to show it, and where), and it should not block the bump.

## Phases

### Phase 1: Bump (`fix(deps):`)

1. Get registry read access. Local `pnpm view` fails: 401 without `NODE_AUTH_TOKEN`, and 403
   with the `gh` token because it lacks `read:packages`. Run
   `gh auth refresh -s read:packages`, then confirm that
   `NODE_AUTH_TOKEN=$(gh auth token) pnpm view @jorgetroya80/donations-api-client versions`
   lists `2.2.0`.
2. Snapshot the current types: copy `node_modules/@jorgetroya80/donations-api-client/dist/` to
   the scratchpad.
3. On branch `chore/bump-api-client-2.2.0`, run
   `pnpm add -E @jorgetroya80/donations-api-client@2.2.0`.
4. Run `diff -r` on the snapshot against the new `dist/`. Expected result: empty, or only
   header/version noise. Any change in a type is a **stop**: list the affected types and grep
   their call sites under `src/` before going further.
5. Run `pnpm run typecheck`, `pnpm run test`, `pnpm run build` and `pnpm run check`.
6. Smoke test against the real API (local fullstack, API image tag `main`): log in, then list
   donors, donations and expenses. Trigger one validation error and confirm field errors still
   map through `parse-api-field-errors.ts`.
7. Commit `fix(deps): bump donations-api-client to 2.2.0`, then open a PR. The body records the
   type-diff result.

### Phase 2 (optional): surface `requestId` (`feat(errors):`)

Only if the product owner wants it. Extend `problemSchema` in `get-problem-message.ts` with
`requestId: z.string().optional()`, and when it is present on 5xx errors append it to the
message ("Error interno. Referencia: …") so users can quote it to support. Add Spanish copy to
`es.json` and unit tests for with and without `requestId`. Separate branch and PR.

## Risks

| Risk                                                                           | Impact | Mitigation                                                                                       |
| ------------------------------------------------------------------------------ | ------ | ------------------------------------------------------------------------------------------------ |
| Kotlin 2.4's annotation-target change alters `required`/`nullable` in the spec | Med    | Step 4 type diff is a hard gate; stop and re-plan if it is non-empty.                            |
| 2.2.0 was not actually published (publish job skipped)                         | Low    | Step 1 confirms the version in the registry before anything else.                                |
| CI cannot install 2.2.0 (token scope)                                          | Low    | CI already installs 2.0.0 from the same registry, so the same token works. Verify on the PR run. |
| MSW handlers drift from the real API shape                                     | Low    | No DTO changed. The Step 6 smoke test covers the real API.                                       |
